# ТЕХНИЧЕСКОЕ ЗАДАНИЕ ДЛЯ ИИ
## Проектирование и реализация Production-Ready Real-Time Data Platform

> **Приоритет этой редакции.** Платформа уже существует, и в ней есть работающий Flink SQL job. Цель — изучить его, устранить выявленные проблемы и внести совместимые изменения в имеющиеся файлы. Все требования ниже применяй к фактической системе: не создавай её заново и не заменяй работающие компоненты только ради соответствия предлагаемой структуре. Если дальнейшие разделы говорят «создай» или «реализуй», сначала проверь, существует ли компонент; существующий компонент изучи, проверь и измени только при доказанной необходимости.

> **Режим для ограниченной офлайн-модели.** Выполняй за один ответ один проверяемый этап или одну связанную группу файлов. Сначала читай предоставленные файлы и фиксируй факты, затем планируй минимальное изменение, после этого выдавай полный патч и проверки. Не пытайся одновременно написать всю платформу по памяти. Не выдумывай поддержку параметров, результаты тестов и содержимое недоступных файлов. Контекст следующего шага передавай через краткий журнал решений и результатов.

### 1. Твоя роль

Выступи в роли команды высококвалифицированных специалистов:

- Principal Data Engineer
- Apache Flink / Flink SQL Architect
- Apache Kafka Architect
- Microsoft SQL Server Performance Engineer
- Java Backend Engineer
- DevOps / SRE Engineer
- Data Platform Security Engineer

Твоя задача — довести существующую платформу и её готовый Flink SQL job до проверенного промышленного состояния, сохранив рабочую бизнес-логику и существующие контракты.

**Не ограничивайся теоретическими рекомендациями. Изменяй реальные SQL-файлы, конфигурации, код, тесты и документацию там, где это требуется установленной целью. Не генерируй замену существующему job без анализа его текущей логики.**

До любых правок запроси или прочитай: полный SQL job, связанные DDL/source/sink definitions, конфигурацию запуска, версии Flink и JAR, пример входного события и схему, текущие метрики/ошибки, ограничения офлайн-контура и ожидаемое поведение после изменения. Если файла нет, не имитируй его содержимое. Укажи точные недостающие материалы и продолжай только с независимыми проверками.

Принимай архитектурные решения с точки зрения производительности, отказоустойчивости, сопровождаемости и возможности эксплуатации без доступа к интернету.

# 2. Исходные требования

## 2.1. Назначение системы

Доработать существующую платформу, обеспечивающую непрерывную обработку событий из Apache Kafka с последующей записью в Microsoft SQL Server. Сначала опиши фактический поток из имеющихся SQL, конфигурации и схем; целевую схему ниже используй как требование для проверки, а не как доказательство того, что она уже реализована.

Основной сценарий:

**Kafka → Apache Flink → Kafka Output → MSSQL Writer → Microsoft SQL Server**

Дополнительные компоненты, наличие и необходимость которых нужно проверить:

- Confluent Schema Registry или совместимый локальный сервис
- S3-совместимое хранилище для checkpoint/savepoint и архивов
- Dead Letter Queue (DLQ)
- Prometheus
- Grafana
- Alertmanager
- Apache Spark для batch/backfill при необходимости

## 2.2. Требования к производительности

Целевые показатели на первоначальном этапе:

| Показатель | Цель |
|---|---|
| End-to-end latency P95 | Не более 5 секунд |
| End-to-end latency P99 | Не более 10 секунд |
| Начальная тестовая нагрузка | 10 000 сообщений/сек |
| Масштабирование | Горизонтальное |
| Потеря подтверждённых данных | Недопустима в пределах модели отказов |
| Повторная обработка | Без некорректного дублирования изменений |
| Работа без интернета | Обязательна |

Показатели должны быть подтверждены нагрузочными тестами. Не выдавай их за гарантированные возможности оборудования.

Перед оптимизацией зафиксируй baseline текущего job: объём накопленного Kafka backlog, число partitions, records/sec и MB/sec на каждой стадии, P95/P99 до SQL commit, CPU/RAM/GC, checkpoint duration и failure, backpressure, Kafka lag, время SQL batch/transaction. Если метрик нет, сначала предложи минимальный способ их снять без изменения бизнес-логики. Целевые 10 000 сообщений/сек — исходная гипотеза, а не требование менять архитектуру до измерений.

## 2.3. История проблемы

В предыдущей конфигурации Apache Flink SQL 2.2 наблюдалась крайне низкая производительность:

- Flink обрабатывал приблизительно 12 000 сообщений за несколько минут.
- Spark Structured Streaming обрабатывал микробатчи до 1 000 000 сообщений.
- Данные поступали из Kafka.
- Использовался Microsoft SQL Server.
- Возникали сложности с типами данных и SQL Server JDBC Dialect.

Не считай установленным фактом, что проблема вызвана Flink или JDBC. Размер Spark micro-batch не равен пропускной способности.

Проведи независимые измерения, чтобы определить настоящие причины.

Существующий SQL job — главный исходный артефакт. Прежде чем предлагать правки, составь его инвентаризацию: все `CREATE TABLE`/`VIEW`, `INSERT`, настройки `SET`, имена топиков, Kafka keys, формат сообщений, типы, фильтры, join/aggregation, watermarks, sink и зависимости. Отмечай, что подтверждено кодом, что подтверждено измерениями и что остаётся гипотезой.

# 3. Архитектурные принципы

Система должна соответствовать следующим требованиям:

1. Каждый компонент отвечает за ограниченный набор задач.
2. Потоковые вычисления отделены от записи в SQL Server.
3. Ни один компонент не должен неконтролируемо терять данные.
4. Все операции повторной обработки должны быть безопасными.
5. Система должна восстанавливаться после сбоев.
6. Конфигурация отделена от программного кода.
7. Все параметры производительности настраиваются без изменения бизнес-логики.
8. Каждая стадия обработки имеет собственные метрики.
9. Подключение новых источников и таблиц не должно требовать переработки всей архитектуры.
10. Проект должен полностью работать в изолированной инфраструктуре.

Следуй принципам KISS, DRY, Separation of Concerns и Infrastructure as Code.

Избегай преждевременного усложнения архитектуры.

Изменения оформляй как минимальный патч к существующим файлам. Не меняй одновременно источник, преобразования и sink, если это не требуется согласованной целью. Для каждого изменения фиксируй инварианты: схема выхода, ключи, порядок, семантика обновлений, обработка некорректных записей и порядок восстановления.

# 4. Обязательная архитектура

## 4.1. Kafka Ingestion

Проверь существующие Kafka topics; создавай или переименовывай их только если соответствующий контракт отсутствует или целевое изменение требует этого:

- `raw.events.v1`
- `processed.events.v1`
- `dlq.events.v1`

При необходимости создавай дополнительные topics для конкретных доменов данных.

Предусмотри:

- Правильный подбор количества partitions.
- Репликацию и настройки отказоустойчивости.
- Retention с учётом максимально допустимого простоя MSSQL.
- Корректную работу consumer groups.
- Partition assignment и rebalance.
- Kafka message keys.
- Контроль producer acknowledgements и retries.
- Контроль consumer lag.
- Безопасный replay.
- Обработку poison messages.

Не выбирай количество partitions произвольно. Предложи метод расчёта по количеству сообщений, их размеру, CPU и требуемому параллелизму.

## 4.2. Apache Flink SQL 2.2

Используй Apache Flink 2.2 как основной движок потоковых вычислений.

**Сначала проанализируй имеющийся job.** Выдай краткую карту `source → операции → sink`, полный список таблиц и зависимостей, фактическую схему каждого промежуточного результата и места, где меняется семантика данных. Сохрани исходный SQL как контрольную версию. Затем сформулируй конкретную гипотезу изменения и покажи минимальный diff. Не переписывай весь job в другой API и не добавляй функции, которых в нём нет, без доказанной необходимости.

Для каждого изменённого SQL-файла предоставь **полный итоговый текст**, а также diff относительно исходного. Если SQL слишком велик для одного ответа офлайн-модели, разбей работу по независимым файлам и веди манифест: обработанный файл, исходный hash/версия, сделанное изменение, результаты проверки, следующий файл. Не сокращай итоговый SQL многоточием или фразой «остальное без изменений».

Реализуй:

- Kafka Source.
- Avro Confluent deserialization.
- JSON как дополнительный поддерживаемый формат.
- Schema validation.
- Data normalization.
- Type conversion.
- Event-time processing.
- Watermarks там, где они действительно необходимы.
- Deduplication при наличии требований к уникальности.
- Stateful processing при необходимости.
- Routing.
- Kafka Sink.
- Обработку ошибочных сообщений.

Отдельно исследуй параметры:

- `parallelism.default`
- `scan.parallelism`
- `pipeline.max-parallelism`
- TaskManager slots
- Kafka consumer fetch settings
- Checkpoint interval
- State backend
- JVM и GC
- TaskManager memory
- Network buffers
- Backpressure
- Operator chaining
- SQL execution plan

Не применяй параметры без проверки их поддержки в конкретных версиях коннекторов.

Создай временные диагностические SQL jobs для проверки производительности **только после того, как зафиксирован baseline существующего job и исключено влияние тестов на production consumer group и топики**:

1. Kafka → Blackhole.
2. Kafka → Kafka.
3. Kafka → преобразования → Blackhole.
4. Kafka → преобразования → Kafka.
5. Полный pipeline до MSSQL.

Для каждого теста измеряй records/sec, bytes/sec, latency и использование CPU/RAM.

## 4.3. Schema Registry и Avro

Реализуй локальное управление схемами.

Обязательно:

- Schema versioning.
- Schema compatibility.
- Проверка совместимости при изменениях.
- Поддержка nullable-полей.
- Корректная обработка DECIMAL.
- Корректная обработка TIMESTAMP и часовых поясов.
- Обработка отсутствующих или некорректных полей.
- Проверка разных версий Avro.
- DLQ для необрабатываемых сообщений.

Не преобразовывай денежные значения в DOUBLE без обоснования.

Обеспечь правильное сопоставление типов Avro, Flink SQL и MSSQL.

# 5. MSSQL Writer — отдельный сервис

Сначала установи, существует ли MSSQL Writer, как он получает события и какие гарантии реально обеспечивает. Если Writer уже есть, проверь и при необходимости доработай его. Если его нет, создай отдельный план и контракт интеграции; реализацию начинай после того, как изменённый Flink SQL job корректно публикует события в Kafka и это подтверждено тестом. Не объявляй Writer завершённым по одному SQL job.

Назначение:

**Читать обработанные события из Kafka и безопасно записывать их в Microsoft SQL Server.**

Технологии:

- Java 21
- Kafka Consumer API
- Microsoft JDBC Driver
- HikariCP при необходимости
- Micrometer / Prometheus
- Maven или Gradle
- Docker

## 5.1. Алгоритм работы

1. Получить сообщения из Kafka.
2. Сформировать пакет.
3. Валидировать данные.
4. Начать транзакцию SQL Server.
5. Проверить идемпотентность.
6. Загрузить данные в staging.
7. Применить изменения к целевым таблицам.
8. Сохранить прогресс Kafka partitions в той же SQL-транзакции.
9. Выполнить SQL commit.
10. Подтвердить Kafka offsets.

Обязательно реализуй восстановление после ситуации, когда SQL commit выполнен, а Kafka offset commit не завершён.

Используй сохранённые в MSSQL offsets как авторитетную позицию уже применённых данных.

Предусмотри корректную работу при Kafka consumer group rebalance, включая отзыв partitions, fencing прежних владельцев и предотвращение конкурентного применения одних и тех же offsets.

## 5.2. Пакетная запись

Реализуй настраиваемые параметры:

- `batch.max.rows`
- `batch.max.bytes`
- `batch.max.wait.ms`
- `jdbc.pool.size`
- `jdbc.query.timeout`
- `writer.instances`
- `retry.max.attempts`
- `retry.backoff.ms`

В качестве начальной гипотезы используй 1 000 сообщений или 200 мс ожидания.

Проведи сравнение:

- JDBC batch INSERT.
- SQL Server Bulk Copy.
- Staging + set-based UPDATE/INSERT.
- Staging + MERGE при обоснованной безопасности.

Определи наиболее производительный и надёжный механизм.

## 5.3. Идемпотентность

Разработай таблицы:

- `events_target`
- `events_staging`
- `processed_events`
- `kafka_offsets`

Используй `event_id`, `event_version` и Kafka topic/partition/offset там, где это соответствует контракту событий.

Гарантируй атомарное применение бизнес-изменений и фиксацию прогресса.

Обрати внимание:

- Одна Kafka partition может содержать множество событий.
- Offsets фиксируются отдельно по каждой partition.
- Старые версии событий не должны перезаписывать новые.
- Повторное выполнение SQL-транзакции должно быть безопасным.
- Повторные event_id должны обрабатываться детерминированно.
- Нельзя создавать пропуски offsets при частичных ошибках.

Не называй обработку exactly-once, если фактически обеспечена только at-least-once delivery с идемпотентными SQL-эффектами.

# 6. Отказоустойчивость

Обязательно реализуй и протестируй следующие сценарии:

| Сценарий | Ожидаемый результат |
|---|---|
| Падает Flink TaskManager | Восстановление из checkpoint |
| Падает Flink JobManager | Восстановление при настроенном HA |
| MSSQL недоступен | Writer не подтверждает необработанные offsets |
| Kafka broker перезапускается | Восстановление соединения |
| Writer падает до SQL commit | Пакет безопасно обрабатывается повторно |
| Writer падает после SQL commit | Изменения не применяются повторно |
| Сообщение некорректно | Контролируемая DLQ-политика |
| Истекает срок Kafka retention | Алерт заранее, описанный recovery plan |
| Kafka rebalance | Корректная передача владения partitions |
| Частичная недоступность сети | Нет неконтролируемой потери или двойного применения |

Настрой:

- Flink checkpoints.
- Savepoints.
- Persistent checkpoint storage.
- Restart strategy.
- Kafka replication.
- Writer retry/backoff.
- Graceful shutdown.
- SQL transaction timeouts.
- Readiness/liveness probes.

Объясни ограничения гарантий при полном разрушении кластера или потере долговременного хранилища.

Система будет работать в инфраструктуре без доступа к интернету.

Проведи инвентаризацию текущего способа развёртывания и имеющихся offline-артефактов. Создай или доработай только недостающие элементы из списка:

- `docker-compose.yml`
- `Dockerfile` для Flink с коннекторами.
- `Dockerfile` для MSSQL Writer.
- Конфигурацию Kafka.
- Schema Registry.
- MinIO при необходимости.
- Prometheus.
- Grafana.
- Alertmanager.
- `.env.example`
- Скрипты развёртывания.

Раздели окружения:

1. Локальная разработка.
2. Интеграционное тестирование.
3. Production.

Docker Compose используй для разработки и интеграционных тестов, если он нужен для проверки изменённого job. Production-платформу не мигрируй на Kubernetes или Flink Standalone HA без анализа существующей инфраструктуры и отдельного обоснования. Укажи, какие артефакты уже есть и какие реально изменены.

Подготовь офлайн-комплект:

- Все необходимые JAR.
- Транзитивные зависимости.
- Docker images.
- SQL scripts.
- Проверенные версии.
- SHA-256 checksums.
- Инструкции по переносу.
- Скрипты `docker load`.
- Скрипты запуска и проверки готовности.

Нельзя использовать `latest` для критичных компонентов.

Все версии должны быть зафиксированы и проверены на совместимость.

Не утверждай, что зависимости скачаны или система проверена, если соответствующие действия реально не выполнялись.

# 9. Производительность и нагрузочное тестирование

Построй воспроизводимый benchmarking framework.

Проведи следующие эксперименты:

| Тест | Назначение |
|---|---|
| Kafka → Blackhole | Определить предел чтения Flink |
| Kafka → Kafka | Проверить обработку и Kafka Sink |
| Kafka → SQL → Kafka | Оценить стоимость преобразований |
| Kafka → MSSQL Writer | Найти предел SQL-записи |
| Полный pipeline | Измерить end-to-end throughput |
| Spark vs Flink | Сравнить движки на равных условиях |

Обязательно соблюдай одинаковые:

- Исходные данные.
- Типы и схемы.
- Размеры сообщений.
- Kafka partitions.
- Выделенные ресурсы.
- Бизнес-преобразования.

# 15. Порядок работы ИИ

Работай последовательно, но сохраняй полный объём требований этого документа. Ограничивай **размер одного шага**, а не глубину итоговой проверки. В каждом ответе указывай текущий этап, изученные файлы, подтверждённые факты, гипотезы, изменения, выполненные проверки и следующий шаг. Если контекст переполнен, продолжай по журналу состояния, не начинай анализ заново.

**Этап 0 — Входной пакет и инвентаризация.** Получи полный существующий SQL job, DDL/схемы, настройки запуска, версии и доступные JAR, пример событий, метрики, логи, текущий способ развёртывания и конкретную цель изменения. Составь карту файлов и зависимостей. При недостатке данных назови до трёх блокирующих материалов; не заполняй пробелы догадками.

**Этап 1 — Baseline и диагноз.** Опиши фактический путь событий, контракты и гарантию доставки. Сними или запроси измерения каждой стадии. Выбери одну проверяемую гипотезу. Не переписывай SQL до определения причины, если речь идёт о производительности.

**Этап 2 — План минимального изменения.** Укажи точные файлы и строки/блоки, которые надо изменить, неизменяемые инварианты, риск для state/checkpoint/savepoint, критерии приёмки и отката. Проверяй поддержку используемых опций на установленных версиях. Не предлагай новые сервисы для решения проблемы, локализованной в одном операторе.

**Этап 3 — Изменение существующего Flink SQL job.** Внеси один связанный патч. Выдай diff и полный итоговый текст каждого изменённого SQL-файла. Сохрани ключи, схему, временную семантику, фильтрацию и типы, если их изменение не является целью. Для любого изменения контракта покажи миграцию и совместимость потребителей.

**Этап 4 — Проверка SQL и локальная интеграция.** Выполни применимые syntax/`EXPLAIN`, проверку типов и схемы, контрольные события, сравнение результата до/после и восстановление после restart. Для производительности сравни Kafka → Blackhole, Kafka → преобразования → Blackhole, Kafka → Kafka и полный путь при одинаковых условиях. Не смешивай диагностические consumer groups с production.

**Этап 5 — MSSQL Writer и корректность записи.** Проверь существующий Writer; если он отсутствует и требуется целевой архитектурой, реализуй его отдельным этапом после подтверждения Kafka output. Проверь транзакции, идемпотентность, offset commit, повтор после сбоя, порядок версий и нагрузку MSSQL. Не заявляй сквозное exactly-once без испытания границы Kafka/MSSQL.

**Этап 6 — Эксплуатация и развёртывание.** Адаптируй имеющиеся Docker/offline-артефакты и мониторинг к изменённому job. Проверь classpath/JAR и отсутствие сетевых обращений в закрытом контуре. Обнови алерты, инструкции запуска и отката, не перестраивая рабочую инфраструктуру без необходимости.

**Этап 7 — Нагрузка и аварии.** Сравни baseline и результат по records/sec, MB/sec, lag, P95/P99 до SQL commit и ресурсам. Проверь сбои Flink, Kafka, Writer и MSSQL, если их поведение затронуто. Фиксируй фактические результаты и не считай ожидаемое поведение пройденным тестом.

**Этап 8 — Итог и документация.** Подготовь список изменённых файлов, итоговый SQL, результаты тестов, незакрытые риски, troubleshooting, recovery runbook и инструкцию offline deploy. Сопоставь каждый критерий готовности с конкретным доказательством.

После каждого этапа проверяй результат, фиксируй обнаруженные проблемы и исправляй их до перехода к зависимым этапам. Если данных или доступа для проверки нет, останови только зависимую часть и явно укажи, что остаётся непроверенным.

# 16. Главные требования к качеству

**Не создавай демонстрационный проект под видом production-ready системы.**

Не используй заглушки, `TODO`, пустые обработчики или фиктивные реализации в компонентах, которые объявляешь завершёнными.

Не придумывай результаты тестирования.

Не заявляй exactly-once без доказательства гарантий.

Не подменяй реальные измерения теоретической производительностью.

Не оптимизируй Kafka, если фактическое узкое место находится в MSSQL.

Не усложняй систему дополнительными сервисами без технического обоснования.

Доработай существующий проект так, чтобы он был понятным, расширяемым и устойчивым для промышленной эксплуатации в изолированном контуре. Не заменяй его новым шаблонным проектом.

**Конечная цель — платформа, которая стабильно обрабатывает поток событий с задержкой до 10 секунд, выдерживает заданную нагрузку, восстанавливается после аварий и обеспечивает корректность данных в Microsoft SQL Server.**
