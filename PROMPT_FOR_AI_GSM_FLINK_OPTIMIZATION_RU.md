Слово «идеальный» трактуй как: корректный, измеренный, воспроизводимый, достаточно быстрый на заданном оборудовании и понятный в сопровождении. Не обещай универсально оптимальную конфигурацию или произвольное число событий/с.

## 4. Контракт логики: сравнить Spark и Flink до оптимизации

Для каждой выходной ветки выпиши: входные поля, фильтры, lookup-ключи, кратность join, выходные поля и их порядок, приведения типов, правила NULL, дедупликацию и агрегацию. Python используй как эталон намерений, но его фактическое выполнение также проверяй: комментарий не заменяет код.

Обязательно проверь следующие известные различия.

**Дедупликация.** Python выполняет `dropDuplicates()`/`distinct()` внутри `foreachBatch`. SQL хранит состояние дедупликации с TTL 1 час. Эти правила не эквивалентны.

```text
Микробатч 1: событие X
Микробатч 2 через 10 секунд: такое же событие X

Дедупликация внутри каждого микробатча: X может выйти дважды.
Потоковая дедупликация с часовым TTL: второй X может быть подавлен.
```

Не удаляй 14 дедупликаций просто ради скорости и не заменяй их произвольным TTL. Для точного соответствия микробатчам нужны явные границы/идентификаторы исходных batches и соответствующие offset ranges. Окно по времени не является точной заменой микробатча.

**ROAD.** Python группирует данные текущего микробатча. SQL использует `TUMBLE(... INTERVAL '60' SECOND)` по processing time. Это другая группировка и дополнительная задержка ожидания закрытия окна. Замена 60 секунд на 1 секунду меняет число и значения выходных строк.

```text
События одного ключа: t=0,2 с и t=1,2 с.
Один исходный микробатч: одна строка COUNT=2.
Окна по 1 с: две строки COUNT=1.
```

Раздели варианты: точное воспроизведение исходного batch-контракта; согласованный новый оконный контракт; ранние обновления результата с upsert/changelog. Для третьего варианта нужна совместимая семантика sink и устойчивый ключ, а не append той же строки при каждом обновлении.

**ALARM.** В SQL одна ветка `out_alarm_tel_from` включена в `UNION ALL` дважды. В предоставленном Python `IDENT_BRANCHES` содержит шесть сопоставлений. Подтверди это тестом на кратность и предложи исправление как отдельное изменение корректности.

**Необычные FROM/TO.** В оригинальном Python намеренно сохранены: lookup по `TEL_TO` в зеркальной not-russian ветке; `IMEI_TO` в проекции BS_TEST/from; `distinct()` только для PULKOVO/from. Не исправляй эти места как «очевидные опечатки» без изменения контракта.

**UID.** Проверь фактическую проекцию: Python читает `UID` справочника, но в соответствующих выходных функциях может использовать `IDENTIFICATOR AS UID`. Следуй реальной проекции, не названию поля.

**Гарантии записи.** Python по умолчанию использует staging/commit-маркеры; SQL напрямую вставляет в JDBC append sink. Это различие корректности после сбоев, даже если результаты без сбоев совпадают.

**Типы и Avro.** Проверь timestamp precision, timezone, BIGINT/STRING, ведущие нули, отрицательные/нулевые значения, schema ID, обработку некорректного framing, DLQ. `TIMESTAMP(3)` и исходный timestamp более высокой точности могут влиять на дедупликацию и сравнение результатов.

Если точный перенос и минимальная задержка требуют несовместимых решений, сформулируй конкретное противоречие и вынеси на выбор только это решение. Остальной анализ продолжай.

## 5. Диагностика скорости и задержки

До заявления «причина найдена» собери baseline. Если доступа к среде нет, подготовь диагностические job и команды, а вывод обозначь как гипотезу.

Разложи путь на измеряемые стадии:

1. Kafka → декодирование Avro → blackhole.
2. Kafka → декодирование → входная дедупликация → blackhole.
3. Kafka → вся логика/lookup → blackhole вместо восьми JDBC sink.
4. Каждая из восьми выходных веток отдельно → blackhole.
5. Полный job → тестовые MSSQL-таблицы.

Blackhole применяй только в диагностике. Печатать каждую запись в stdout для нагрузки нельзя: логирование само станет ограничителем.

Сравнивай один и тот же набор Kafka partition/offset ranges, размер сообщений и версии справочников. Зафиксируй холодный и прогретый запуск отдельно. Новые группы с `latest-offset`, запущенные в разные моменты, не обеспечивают воспроизводимый набор данных.

Не запускай несколько сравнительных вариантов одновременно на одном ограниченном стенде и не объясняй разницу конфигурацией, если изменились ресурсы или состав входа. Для каждого эксперимента меняй один фактор либо явно обоснуй связанный набор.

Собирай: входные события/с и МБ/с, выход по каждой ветке, lag и его производную, busy/idle/backpressure, latency lookup, cache hits/misses, число SQL запросов, SQL query duration и logical reads, batch insert/commit duration, CPU/heap/GC/direct memory, диск RocksDB, checkpoint duration/size/failures.

Пример корректного вывода:

```text
Факт: source → blackhole выдержал N событий/с на одном фиксированном наборе.
Факт: полная логика → blackhole дала M событий/с.
Наблюдение: lookup-оператор занят, cache miss высокий; SQL-запросы занимают P мс.
Гипотеза: lookup ограничивает throughput.
Проверка: тот же набор с локальной версией справочника.
```

Не называй отсутствие backpressure доказательством отсутствия проблем: блокирующий lookup может выглядеть как busy. Не дели число строк одной выходной таблицы на время и не называй результат скоростью чтения Kafka: фильтры и join меняют кратность.

## 6. Выбор архитектуры lookup для низкой задержки

Главное различие исходников: Spark сохраняет загруженные справочники и переиспользует локальные данные; Flink SQL использует JDBC lookup с PARTIAL cache. При промахах кэша возможен синхронный сетевой запрос. Подтверди режим по конкретной версии connector.

Оцени варианты с учётом размера и изменчивости справочников:

- существующий JDBC lookup: подходит, если есть эффективный поиск по индексу, приемлемая задержка и достаточный hit rate;
- неизменяемые локальные snapshot + индекс: подходит, если правила можно обновлять между запусками и они помещаются в память/локальный индекс;
- асинхронный lookup: только при реальной поддержке используемым API/connector, с ограниченной конкуренцией и timeout;
- CDC/поток обновлений справочников + управляемое состояние: для непрерывно меняющихся правил, с согласованной bootstrap- и recovery-семантикой;
- подготовленные индексируемые таблицы вместо дорогих views: после анализа определений views и планов SQL Server.

Не утверждай, что для JDBC SQL достаточно включить выдуманный `lookup.async=true` или `lookup.cache=FULL`. Проверь поддерживаемые опции. Если нужен собственный Java-компонент, объясни, какую проблему он решает и почему встроенного механизма недостаточно.

Для локального snapshot обеспечь: версию, manifest/hash, неизменяемую папку, одинаковую версию на всех узлах, проверку схемы, отказ на неполной загрузке, способ обновления и привязку snapshot к версии job/savepoint. Если views выгружены последовательно, не называй это общим транзакционным снимком.

Ключ должен отображаться в **список совпадений**, если справочник не уникален:

```text
Ключ K → [строка A, строка B, строка B]
INNER JOIN для одного входного K должен дать 3 строки.
Map<K, Row> потеряет кратность.
Удаление дубликата B без основания изменит результат.
```

SQL NULL не равен другому NULL при обычном equi-join. Нулевой идентификатор не следует автоматически отбрасывать, если исходная ветка это допускает.

Пример формы SQL с локальной табличной функцией — только иллюстрация API:

```sql
SELECT c.TEL_TO, d.idident, d.GP
FROM billing AS c
LEFT JOIN LATERAL TABLE(dim_msisdn(c.TEL_TO)) AS d ON TRUE;
```

При реализации TableFunction проверь типизацию, жизненный цикл `open`, classloader, восстановление, передачу конфигурации и отсутствие мутации общих Row. Не выполняй JDBC-вызов внутри `eval` на каждое событие, если заявлено устранение сетевого lookup.

Рассчитай память всех индексов на каждый процесс/classloader, включая строки и коллекции. Лимит «500000 строк» не гарантирует фиксированный объём heap. Общие справочники не становятся частью RocksDB автоматически. Если snapshot не помещается, предложи иной способ хранения; не отключай проверки и не загружай неограниченный объём в память.

## 7. Оптимизация SQL-графа без потери результатов

Изучи физический план. Common view или CTE не гарантирует однократного вычисления и переиспользования результата. Сопоставь число source scans, lookup-операторов, exchange/shuffle, дедупликаций и sink с текстом SQL.

Проверь возможность:

- переиспользовать два join по `TEL_FROM`/`TEL_TO` между несколькими OSS-ветками;
- вынести общие проекции и безопасно протолкнуть фильтры;
- объединить однотипные identifier-поиски через нормализацию шести полей;
- избежать повторной сериализации тяжёлых полей;
- сократить избыточное состояние только при доказанной логической эквивалентности.

Пример нормализации identifier-полей:

```text
Одна исходная запись →
  (branch=tel_from, type=2, value=TEL_FROM)
  (branch=tel_to,   type=2, value=TEL_TO)
  (branch=imsi_from,type=19,value=IMSI_FROM)
  (branch=imsi_to,  type=19,value=IMSI_TO)
  (branch=imei_from,type=20,value=IMEI_FROM)
  (branch=imei_to,  type=20,value=IMEI_TO)
```

Этот приём может сократить число независимых lookup-операторов, но увеличивает число строк перед общим оператором и может изменить распределение нагрузки. Не обещай ускорение без теста. Сохраняй `branch_id` до той точки, где требуется различать дубликаты из разных веток. Замена шести независимо дедуплицированных веток одной общей `DISTINCT` может потерять законные повторы.

Не заменяй `UNION ALL` на `UNION`, `LEFT JOIN` на `INNER JOIN`, не меняй условия NULL и порядок выходных столбцов без доказательства. Не добавляй выдуманный `PRIMARY KEY ... NOT ENFORCED` для подавления ошибок planner.

Проверь checkpoint и state, но не сокращай интервал автоматически. Processing-time first-row dedup не обязана ждать час перед выдачей строки: TTL относится к хранению состояния, а не размеру batch. Интервал checkpoint также не является универсальным интервалом JDBC flush.

## 8. MSSQL: чтение, запись и реальная гарантия доставки

Для lookup проверь планы запросов по реальным ключам: `ident`; `(TYPE, IDENTIFICATOR)`; `(CODE, LAC, CELLID)`. Это список предикатов для исследования, а не разрешение создавать одинаковые индексы вслепую. Изучи underlying tables/views, типы, implicit conversion, cardinality, logical reads, ожидания и блокировки. Не добавляй `NOLOCK` как универсальную оптимизацию.

Для sink измерь batch insert и SQL commit отдельно. В исходном SQL ожидаются `max-rows=500`, `interval=1s`, `parallelism=2` для каждой таблицы. Проверь это. Восемь sink по два subtask уже могут создавать значимую конкуренцию с чтением справочников.

Не увеличивай одновременно batch size, parallelism и количество соединений. Большой batch может улучшить throughput и ухудшить p99. Частый flush может снизить задержку и увеличить нагрузку на журнал транзакций. Для тестов используй репрезентативные индексы и триггеры: пустая heap-таблица может дать ложное представление.

Microsoft JDBC bulk copy рассматривай как отдельный эксперимент. Проверь версию драйвера, SQL-форму insert, identity/default/NULL, constraints и триггеры. Если нужен staging, включай bulk copy в проверенный staging-путь, не меняя незаметно поведение целевых таблиц.

Если выбран отдельный MSSQL Writer, реализуй его полностью:

- ограниченные batch по числу строк, байтам и времени;
- bounded concurrency и pool;
- согласованное подтверждение offsets;
- транзакционную запись результата и прогресса в MSSQL либо другой доказанный протокол;
- восстановление после DB commit до Kafka offset commit;
- обработку rebalance/отзыва partitions;
- fencing старого владельца, если конкурирующие владельцы могут писать один partition;
- явную DLQ-политику и возможность replay;
- метрики очередей, задержек, retry и commit.

Не запускай старый прямой JDBC job и новый Writer одновременно в одни таблицы без плана миграции.

Пример аварии, которую обязан выдерживать выбранный протокол:

```text
1. Writer получил partition=3, offsets 100..199.
2. MSSQL commit прошёл.
3. Процесс упал до подтверждения Kafka offset.
4. После рестарта события прочитаны повторно.
Требование: нет потери, а эффект повторной записи соответствует контракту.
```

`execution.checkpointing.mode=EXACTLY_ONCE` не делает внешний append JDBC sink автоматически exactly-once. Уникальный ключ тоже нельзя выдумывать: два одинаковых по значениям события могут быть законными двумя событиями. Идентификатор операции должен учитывать источник, преобразования, кратность и бизнес-контракт.

## 9. Kafka, Schema Registry и бюджет задержки

Сохрани Avro Confluent wire format и проверь фактическую schema compatibility. Не меняй формат на JSON только ради простоты примера. Перенеси или явно переопредели правила обработки schema ID, ошибочного сообщения и DLQ из Python.

Уточни startup mode и replay. В существующем SQL `latest-offset` при новом старте без checkpoint означает чтение новых данных. Это может замаскировать backlog. `max.poll.records=500` не является ограничением «500 сообщений в секунду». Изменение fetch-параметров обосновывай размером сообщений, сетью и измерением ожиданий.

Kafka source эффективно ограничен числом partitions. Изменение partitions может менять распределение ключей/порядок — это отдельное решение. Не увеличивай Flink parallelism до 32 только потому, что число выглядит производительно.

Если используется выход Kafka с exactly-once, нужен `read_committed` downstream. Видимость транзакционных записей зависит от успешного checkpoint/commit; checkpoint 10 или 60 секунд может конфликтовать с p95 ≤ 5 секунд на этом пути. Рассчитай бюджет задержки до MSSQL, а не только обработку внутри Flink. Не решай это отключением гарантий без согласованного изменения контракта.

```text
L_end_to_end =
  ожидание/чтение Kafka
  + очередь и обработка Flink
  + ожидание окна, если оно есть
  + ожидание видимости Kafka-транзакции, если она есть
  + очередь Writer/буфер JDBC
  + время записи и commit MSSQL.
```

Прямой JDBC sink и транзакционный Kafka sink имеют разные механизмы видимости. Не переноси выводы о checkpoint-задержке одного пути на другой.

## 10. Compose, Dockerfile и ресурсы

Выдай Compose для реально выбранной архитектуры и укажи, какие сервисы внешние. Не включай несуществующий `writer` image без исходников и способа его собрать.

Зафиксируй версии образов, Java и JAR. Избегай `latest`. Для исходной ветки рассматривается Flink 2.2/2.2.1; фактическую версию и доступные артефакты проверь. Более новая версия не считается автоматически более подходящей.

Пример согласованного распределения, **не готовая рекомендация для неизвестного сервера**:

```yaml
# Иллюстрация части environment/ресурсов одного TaskManager:
environment:
  FLINK_PROPERTIES: |
    jobmanager.rpc.address: jobmanager
    taskmanager.numberOfTaskSlots: 4
    taskmanager.memory.process.size: 6144m
    parallelism.default: 8
mem_limit: 8g
cpus: 4
```

Два таких TaskManager дают восемь слотов и до 16 GiB лимитов контейнеров; отдельно нужны JobManager, ОС и другие сервисы. Слоты не равны выделенным CPU. Укажи минимальный ресурсный профиль, запас памяти и способ адаптации к фактическому железу.

Учти:

- `SET` в SQL может изменить параметры job относительно кластерного конфига: проверь эффективную конфигурацию;
- нельзя монтировать папку только дополнительных JAR поверх всего `/opt/flink/lib`;
- одинаковые connector/UDF должны быть доступны SQL Client и кластеру;
- `localhost` внутри контейнера — сам контейнер;
- `depends_on` не доказывает готовность сервиса;
- секреты не должны попадать в Git, открытый Compose и публичные логи;
- переменные среды Compose не подставляются автоматически внутрь `job.sql`;
- локальный Docker volume не является общим хранилищем на нескольких хостах;
- `restart: unless-stopped` перезапускает контейнер, но не доказывает восстановление session job;
- SQL Client submission, application lifecycle и HA должны соответствовать выбранной модели запуска;
- `docker compose config` проверяет конфигурацию, но не компилирует SQL и не проверяет connectors.

Если используешь конфигурацию через `FLINK_PROPERTIES`, объясни приоритеты и не держи расходящиеся значения в нескольких местах. Если используется bare metal, дай эквиваленты в `config.yaml` и системных ограничениях.

## 11. Офлайн-поставка и воспроизводимость

Подготовь полный manifest: версии/хэши образов и JAR, архитектура CPU, Java, SQL, конфиги, snapshot rules, входная Avro-схема и средства сборки.

Сборка/запуск в изолированном контуре не должны обращаться к интернету. Все скачивания выполняются заранее в разрешённой среде. Укажи точные команды `docker save/load`, проверки SHA-256 и локальной сборки; названия архивов должны соответствовать реально подготовленным файлам.

Для Java-компонента предоставь исходники, сборку, зависимости и совместимый собранный JAR, если реально можешь его собрать. Не добавляй сборочные копии Flink core поверх штатного runtime classpath. Если offline Maven требует локального репозитория, включи его или предложи проверенный альтернативный путь сборки.

Обеспечь доступность локального Schema Registry и его схем. Для восстановимого snapshot-варианта переносится вся версия справочников с manifest. Папка с README и отсутствующими JAR — это исходный комплект, а не готовая офлайн-поставка; обозначай статус точно.

## 12. Мониторинг и оценка SLO

Исходные целевые ориентиры проекта: p95 ≤ 5 секунд, p99 ≤ 10 секунд, начальный нагрузочный ориентир 10 000 входных сообщений/с. Это цели для проверки, а не гарантированные возможности оборудования. Для веток с окнами отдельно согласуй задержку после закрытия окна и полную задержку от входа. Нельзя объявлять весь pipeline соответствующим 5 секундам при обязательном финальном окне 60 секунд.

Подготовь шаблоны Prometheus/Grafana и объясни, откуда берётся каждая метрика. Имена/labels проверяй по реальному `/metrics`. Не выдумывай готовые PromQL для несуществующих метрик. Убедись, что Prometheus видит каждую реплику TaskManager.

Нужны панели:

- вход Kafka и lag по partition;
- выход каждой ветки, коэффициент размножения/фильтрации;
- p50/p95/p99 сквозной задержки до появления результата в MSSQL;
- busy/backpressure/idle и очереди;
- snapshot load time/rows/bytes/version либо JDBC hit/miss и lookup duration;
- heap/GC/RocksDB/disk/CPU/container restarts;
- checkpoint duration/age/failures/state size;
- JDBC/Writer batch duration, rows/batch, retries, DB commit;
- SQL Server waits, deadlocks, transaction log и IO;
- число invalid/DLQ и проверка потерь/кратности.

Для latency используй отдельное время создания/ввода тестового события и согласованное время commit. Исторический `DATE_TIME` может означать время моделируемого события и не подходит как единственная метка задержки обработки replay. Проверь синхронизацию часов.

Не помещай высококардинальные идентификаторы событий в labels Prometheus. Корреляцию тестовых событий веди через ограниченный тестовый набор/логи/проверочные таблицы.

## 13. Тесты корректности и производительности

Сначала создай небольшой детерминированный набор игровых событий и справочников с ожидаемыми результатами по всем восьми sink. Эталон формируй из фактической логики Python и согласованных изменений. Не копируй ошибку SQL одновременно в реализацию и тест.

Сравнивай результаты как мультимножества: значения **и количество повторов**. `set(rows)` может скрыть ошибку `UNION ALL`.

Обязательные случаи:

1. Ключ отсутствует в справочнике; поведение LEFT/INNER join различается.
2. Ключ имеет два разных совпадения и два одинаковых совпадения.
3. NULL, ноль, равные TEL_FROM/TEL_TO, границы диапазонов номеров.
4. Каждая из шести identifier-веток и совпадения нескольких веток одновременно.
5. Строки, пустая строка, Unicode, кавычки, табуляция, переносы в справочнике.
6. Временная точность и timezone на границах суток/окон.
7. Одинаковые события внутри и между batches/TTL-границами.
8. Подтверждённые необычные FROM/TO и асимметрия PULKOVO.
9. ROAD: min/max/count с учётом выбранного контракта.
10. Avro schema mismatch, некорректное сообщение, DLQ/replay.
11. Изменение справочника и повторное восстановление с той же версией правил.
12. Повтор после DB commit и до подтверждения offset.

Пример проверки кратности:

```python
from collections import Counter

# Только пример подхода: нормализуй типы и timestamp явно.
assert Counter(actual_rows) == Counter(expected_rows)
```

Для новой Java-логики проверяй не только map lookup, но и связь с Flink API: типизацию, несколько emitted rows, NULL, lifecycle, сериализацию и изоляцию изменяемых Row. Для SQL нужна проверка planner с фактическими JAR; структурный diff её не заменяет.

Нагрузочный тест должен включать прогрев, устойчивую нагрузку, всплеск и backlog catch-up. Приложи длительность, входной объём/размер, распределение ключей, версии справочников, ресурсы и результаты. Не используй равномерно случайные ключи как единственное приближение реальной игровой нагрузки, если есть горячие ключи.

## 14. Аварии, переключение и откат

Проверь потерю TaskManager, JobManager, соединения Kafka/Registry/MSSQL, недоступность state storage, нехватку диска, повреждение/отсутствие snapshot, истечение Kafka retention, повторные ошибки одного сообщения и rebalance Writer, если он существует.

Для каждого сценария укажи ожидаемый эффект, способ обнаружения, процедуру восстановления, возможный replay и проверку результата. Различай restart контейнера, restart job и восстановление его состояния.

Изменение JDBC temporal join на UDTF или изменение дедупликации может изменить граф операторов/state mapping. Не считай старый savepoint автоматически совместимым. Отдельно проверь восстановление либо разработай контролируемый старт с фиксированных offsets и защитой целевых таблиц от повторов.

Перед переключением зафиксируй: версии кода и правил, offsets/state, резервный рабочий комплект, критерии остановки нового варианта и порядок отката. Тестовая запись должна идти в изолированные таблицы либо иметь доказанный способ безопасного повторного применения. Не предлагай `TRUNCATE`, удаление checkpoint или сброс consumer group как штатную оптимизацию.
